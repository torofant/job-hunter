# M0.11 — Final Implementation Specification

## 1. Purpose

This document is the implementation source of truth for Job Hunter after the completion of milestone M0.

Its purpose is to consolidate the architectural, functional and technical decisions already closed during M0 so implementation can begin without reinterpreting those decisions.

The project objective is to automate the detection, filtering, analysis and prioritization of relevant job offers, notifying the user when an opportunity deserves attention.

The system must remain simple until complexity is justified.

---

## 2. Implementation principles

### 2.1 General principles

- Prefer simple, readable and maintainable solutions.
- Do not introduce complexity unless it solves a demonstrated problem.
- Deterministic business rules belong to the application, not to the AI prompt.
- AI is used only where it provides clear value.
- The system must explain why an offer is relevant.
- Prefer false positives over false negatives during the initial matching/scoring stage.
- Unknown information must not automatically become a negative result.
- Preserve processing history.
- Keep the project suitable for a junior developer with professional experience.

### 2.2 Code style

The project should look like the work of a junior developer with professional experience: clear, correct, tested and maintainable, without unnecessary architectural sophistication.

Avoid:

- unnecessary abstractions;
- excessive design patterns;
- microservices;
- clever or difficult-to-read code;
- unnecessary dependencies;
- comments that only describe obvious code.

### 2.3 Comments

Only two types of comments are used.

#### Section comments

Used to visually separate meaningful sections of a file and act as an internal title.

Example:

```js
// ─── ESTRUCTURA MENSAJE TELEGRAM ─────────────────────────────
```

#### Functional multiline comments

Used only when a short explanation is useful to remember how something works or why it exists.

Example:

```js
/*
 * Se mantiene el mensaje original cuando Claude falla para que
 * un fallo puntual de IA no detenga el procesamiento.
 */
```

Do not comment every function, variable or obvious operation.

## 5. Main responsibilities

### n8n

n8n is a thin integration adapter.

It is responsible for:

- reading Gmail alerts;
- identifying the source;
- extracting offers using source-specific logic;
- creating one `RawJobInput` per valid offer;
- calling `POST /api/jobs`;
- reporting extraction failures to the user.

It does not contain Job Hunter business rules.

### Job Hunter

Job Hunter owns:

- validation;
- normalization;
- deduplication;
- filtering;
- matching;
- scoring;
- coverage;
- confidence;
- prioritization;
- persistence;
- Telegram notifications.

### PostgreSQL

PostgreSQL stores:

- raw inputs;
- detections;
- job offers;
- analyses;
- processing runs;
- AI usage;
- notifications.

### Claude

Claude is an auxiliary normalization/enrichment service.

Claude does not decide:

- whether an offer is rejected;
- whether a requirement matches;
- the score;
- the priority.

Those decisions belong to deterministic application logic.

## 6. End-to-end processing flow

### 6.1 Input

Two ingestion paths exist:

1. Gmail → n8n → Job Hunter.
2. Manual HTTP request → Job Hunter.

Both produce the same `RawJobInput`.

### 6.2 Detection

The API:

1. validates the request;
2. stores the `RawJobInput`;
3. creates the `JobDetection`;
4. creates a `ProcessingRun`;
5. returns HTTP 202;
6. processes the detection asynchronously.

One failed detection must not stop other detections.

### 6.3 Normalization

Normalization converts raw source information into the internal `JobOffer` structure.

The intended order is:

```text
RawJobInput
  ↓
Normalization
  ↓
JobOffer candidate
  ↓
Deduplication
```

If Claude fails, the original input is used as fallback where possible and processing continues. Coverage/confidence may be lower.

If the raw input itself is invalid, preserve the raw input and mark the processing as failed. Do not fabricate a normalized offer.

### 6.4 Deduplication

Deduplication uses simple deterministic signals:

1. `source + source_job_id`
2. normalized URL
3. secondary basic-data signals

No embeddings or complex fuzzy algorithms are used.

When a duplicate is detected:

- reuse the existing `JobOffer`;
- retain the new detection;
- retain processing history;
- do not create a new offer;
- do not generate a duplicate notification.

Known new information may update an existing offer.

Known values must never be replaced by null/unknown.

### 6.5 Filtering

Filtering is executed before matching and scoring.

Hard filters:

- internship/practice;
- scholarship;
- trainee;
- temporary contract;
- self-employed/autónomo;
- irrelevant job family;
- hardware support/repair;
- onsite location beyond 75 km.

All applicable rejection reasons should be collected rather than stopping after the first reason.

Rejected offers remain persisted but are not notified.

Unknown information does not automatically cause rejection.

Reason codes:

```text
INTERNSHIP
SCHOLARSHIP
TRAINEE
TEMPORARY_CONTRACT
SELF_EMPLOYED
IRRELEVANT_JOB_FAMILY
HARDWARE_SUPPORT
ONSITE_TOO_FAR
```

Unknown classification values may use:

```text
UNKNOWN_EMPLOYMENT_TYPE
UNKNOWN_JOB_FAMILY
UNKNOWN_LOCATION
```

### 6.6 Matching

Matching compares the normalized offer against `UserProfile`.

Possible requirement results:

```text
MATCH
PARTIAL
MISSING
UNKNOWN
N/A
```

Semantics:

- MATCH = 100%
- PARTIAL = 70%
- MISSING = 0%
- UNKNOWN = excluded from denominator
- N/A = excluded

Experience is matched according to actual task, technology and context rather than only total years.

The user's experience is separated conceptually into:

- total professional experience;
- explicit development experience;
- technically relevant experience.

The system must not treat all professional experience as full-time developer experience.

### 6.7 Scoring

Total score is 0–100.

Weights:

| Category | Weight |
|---|---:|
| Job family/type | 20% |
| Technologies | 25% |
| Experience | 20% |
| Location/modality | 15% |
| Employment conditions | 10% |
| Languages | 5% |
| Other requirements | 5% |

Job family/type:

- family = 8%
- role = 12%

Technologies:

- required = 17.5%
- preferred = 7.5%

Experience:

- general = 10%
- specific = 10%

Employment conditions:

- salary = 5%
- contract = 3%
- working hours = 2%

Location:

- modality = 10%
- locality = 5%

Seniority is not scored.

Score categories:

```text
80–100  HIGH MATCH
65–79   GOOD MATCH
50–64   POSSIBLE MATCH
0–49    LOW MATCH
```

There is no scoring-based rejection category. Rejection is performed by hard filters.

### 6.8 Salary

Salary preferences:

```text
Minimum: 20,000 EUR
Desired: 24,000 EUR
```

Salary matching:

- below 20,000 → MISSING;
- 20,000–23,999 → PARTIAL;
- 24,000 or more → MATCH;
- unknown → excluded from denominator.

For part-time positions, salary is evaluated using the existing salary rules. No full-time-equivalent normalization is introduced in MVP.

### 6.9 Location

Location score is 15 points.

```text
Location
├── Modality = 10
│   ├── Remote   → 10
│   ├── Hybrid   → 8
│   ├── Onsite   → 5
│   └── Unknown  → UNKNOWN
│
└── Locality = 5
    ├── Remote Spain     → 5
    ├── Castellón        → 5
    ├── Valencia hybrid  → 4
    ├── ≤25 km           → 4
    ├── 26–50 km         → 3
    ├── 51–75 km         → 2
    └── >75 km           → REJECT
```

Examples:

- Remote Spain = 15/15
- Hybrid Castellón = 13/15
- Hybrid Valencia = 12/15
- Onsite Castellón = 10/15
- Onsite 20 km = 9/15
- Onsite 40 km = 8/15
- Onsite 70 km = 7/15
- Onsite >75 km = rejected

Unknown location information must not receive an artificial zero penalty.

### 6.10 Employment conditions

```text
Full-time      → MATCH
Part-time      → PARTIAL
Unknown        → UNKNOWN
Temporary      → REJECT
Internship     → REJECT
Scholarship    → REJECT
Trainee        → REJECT
Self-employed  → REJECT
Freelance      → allowed
```

### 6.11 Coverage

Coverage measures information availability, not job fit.

It is not a multiplier of the score.

Values:

```text
FULL      = 100
LIMITED   = 50
UNKNOWN   = 0
N/A       = excluded
```

Weights:

- Family/Role = 40/60
- Technology/Experience/Languages/Other = 70/30

Coverage and confidence are independent concepts.

### 6.12 Confidence

Confidence represents the reliability of the analysis, not the suitability of the job.

Possible levels:

```text
HIGH
MEDIUM
LOW
```

Confidence is deterministic and must not be selected by Claude.

### 6.13 Prioritization

Prioritization is dynamic and does not require a separate score/entity.

Order:

1. Score descending.
2. If score difference is ≤3 points, Coverage descending.
3. Confidence descending.
4. Detection time descending.

Reasons:

```text
higher_score
similar_score_higher_coverage
similar_score_higher_confidence
same_score_newer_offer
```

## 9. API contract

### POST /api/jobs

Purpose: accept one `RawJobInput`.

Request:

```json
{
  "source": "linkedin",
  "source_job_id": "optional-id",
  "title": "Example job",
  "company": "Example company",
  "url": "https://example.com/job",
  "description": "Optional description",
  "location": "Castellón",
  "detected_at": "2026-09-22T10:00:00Z",
  "raw_metadata": {}
}
```

Required:

- `source`
- `title`
- `company`
- `url`
- `detected_at`

Optional:

- `source_job_id`
- `description`
- `location`
- `raw_metadata`

Authentication:

```text
Authorization: Bearer <API_KEY>
```

Responses:

```text
202 Accepted
400 Bad Request
401 Unauthorized
500 Internal Server Error
```

Accepted response:

```json
{
  "status": "accepted",
  "detection_id": "det_123"
}
```

The API is asynchronous. HTTP 202 means the input was accepted, not that processing has completed.

Duplicates also return 202.

## 10. Gmail and n8n integration

One valid job offer in an email produces one `RawJobInput`.

If an email contains multiple valid offers:

```text
1 email
  ↓
n valid offers
  ↓
n RawJobInput
```

If the email does not contain a valid job offer:

- do not create an empty `RawJobInput`;
- n8n informs the user of the failure.

The failure notification should include, where available:

- source;
- email subject;
- date/time;
- sender;
- failure reason/type;
- original email reference.

There is no `Email` entity in the data model.

Source-specific extractors are preferred over a universal intelligent email extractor.

## 12. AI implementation

Initial provider:

```text
Anthropic
```

Initial model:

```text
Claude Haiku 4.5
```

Configuration:

- one enrichment call per offer per normalization run;
- thinking disabled;
- structured output;
- Zod validation in the application;
- official Anthropic TypeScript SDK;
- prompt stored in the repository;
- prompt version stored explicitly.

No initial:

- multi-provider abstraction;
- model router;
- prompt management entity;
- caching;
- batch processing.

### Claude failure

If Claude fails:

1. preserve the original input;
2. continue processing when possible;
3. use available raw information as fallback;
4. allow Coverage/Confidence to reflect the reduced information quality.

Claude never controls hard filtering, matching decisions, scoring or priority.

## 13. Errors, retries and recovery

### General

One offer failing must not stop processing of other offers.

### API errors

Do not retry:

- HTTP 400;
- HTTP 401.

Retry temporary failures such as:

- HTTP 500;
- network failures.

Maximum:

```text
2 additional retries
```

### Internal processing

Temporary internal failures may receive up to two additional retries.

After the retry limit, the processing run becomes `FAILED`.

### Telegram

Telegram failures do not make the job-processing pipeline fail.

The notification can remain `FAILED` independently.

### Recovery after restart

A periodic internal processor checks recoverable `PENDING`/processing work after restart.

This is database-state recovery, not a distributed queue.

### Manual reprocessing

Manual reprocessing:

- creates a new `ProcessingRun`;
- creates a new `JobAnalysis`;
- retains the previous analysis.

## 14. Telegram notifications

Telegram is the only notification channel in MVP.

Job Hunter communicates directly with the Telegram Bot API.

A `Notification` represents the logical notification for an offer.

Physical Telegram messages may contain up to five offers.

Rules:

- only offers that pass hard filtering can be notified;
- duplicates do not generate a new notification;
- changes to an already notified offer do not automatically trigger a new notification in MVP;
- messages should be concise and actionable.

The threshold for a batch is five offers.

The exact flush behavior for fewer than five offers is a notification-phase implementation detail and does not change the data model.
